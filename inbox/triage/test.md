# SelectionSort Worst-Case Runtime Analysis Report

## 1. 實驗目的

驗證 SelectionSort 演算法在 worst-case 輸入下的執行時間，並與理論時間複雜度 **O(n²)** 進行對照。透過實證量測，觀察實際執行時間是否呈現二次函數成長趨勢。

---

## 2. 實驗方法

### 2.1 演算法實作

- **演算法**：迭代版 SelectionSort（參考 Program 1.8 風格）
- **語言**：C++
- **實作細節**：
  - 外層迴圈：從位置 0 到 n-2
  - 內層迴圈：在未排序部分尋找最小值
  - 每次迭代將找到的最小值與當前位置交換
  - **不使用** `std::sort` 或其他標準庫排序函數

### 2.2 Worst-Case 輸入設計

對於 SelectionSort：
- **比較次數固定**：無論輸入順序如何，總是執行 (n-1) + (n-2) + ... + 1 = n(n-1)/2 次比較
- **Worst-case 定義**：雖然比較次數不變，但資料搬移/交換在不同輸入下會有差異
- **本實驗採用**：**嚴格遞減序列** [n, n-1, ..., 2, 1]
  - 此為教科書常見的 worst-case 範例
  - 每次迭代都需要將最小元素從後方搬移到前方
  - 最大化了資料移動的成本

### 2.3 測點設計

**測試範圍**：n ∈ [0, 3000]

**測點集合**：
```
N = {0, 1, 2, 3, 5, 8, 10, 20, 50, 100, 200, 400, 600, 800, 1000, 1500, 2000, 2500, 3000}
```

**量測流程**（每個 n）：
1. **Warmup**：3 次預熱執行（不記錄）
   - 目的：讓 CPU 快取熱身、消除冷啟動效應
2. **正式量測**：5 次重複執行
   - 每次重新生成遞減序列
   - 使用 `std::chrono::steady_clock` 量測單次排序時間
   - 記錄單位：**微秒 (μs)**
3. **結果**：取 5 次量測的平均值

### 2.4 實驗環境

- **編譯器**：Clang/GCC (C++11 以上)
- **編譯旗標**：`-O2` (啟用優化，但不影響演算法正確性)
- **執行模式**：單執行緒
- **量測工具**：`std::chrono::steady_clock`（高精度、單調時鐘）

## 4. 結果討論

### 4.1 時間複雜度驗證

**理論分析**：
- SelectionSort 的比較次數：
  ```
  C(n) = (n-1) + (n-2) + ... + 1 = n(n-1)/2 = O(n²)
  ```
- 交換次數：最多 n-1 次（每次迭代至多一次交換）
- **總時間複雜度**：**O(n²)**（比較次數主導）

**實驗觀察**（基於實測數據）：
1. **極小 n 區域 (n ≤ 20)**：
   - 執行時間接近 0 μs，受計時器精度限制
   - 演算法開銷極小，無法精確量測
   - 常數項與計時誤差主導
   
2. **小至中等 n (20 < n ≤ 200)**：
   - 二次成長開始顯現
   - n = 50: 1.00 μs
   - n = 100: 6.80 μs
   - n = 200: 30.00 μs
   - 從 100→200（2倍），時間增長 4.41 倍（接近 2²）

3. **中至大 n (200 < n ≤ 1000)**：
   - **明確的二次曲線成長**
   - n = 400: 133.00 μs
   - n = 600: 676.60 μs  
   - n = 800: 1042.80 μs
   - n = 1000: 1522.00 μs

4. **大 n (n > 1000)**：
   - **穩定的 O(n²) 成長模式**
   - n = 1500: 2792.20 μs
   - n = 2000: 3992.80 μs
   - n = 2500: 5835.40 μs
   - n = 3000: 8340.80 μs
   - 從 1000→3000（3倍），時間增長 5.48 倍（接近 3² = 9，考慮系統誤差）

### 4.2 Worst-Case 設計合理性

**為何選擇遞減序列？**
1. **比較次數固定**：
   - SelectionSort 無論輸入如何，總是執行 n(n-1)/2 次比較
   - 這點與 InsertionSort（最佳 O(n)、最差 O(n²)）不同

2. **資料搬移影響**：
   - 雖然比較次數相同，但交換/賦值操作可能受輸入影響
   - 遞減序列：每次都需將最小元素從後方移到前方
   - 最大化了 cache miss 與記憶體存取成本

3. **與其他排序比較**：
   - **InsertionSort**：最佳 O(n)（已排序），最差 O(n²)（遞減）
   - **BubbleSort**：最佳 O(n)（已排序+提前終止），最差 O(n²)（遞減）
   - **SelectionSort**：無論輸入，皆 O(n²)（無自適應能力）

### 4.3 實測與理論的一致性

**驗證方式**：檢查 T(n) / n² 是否趨近常數

從實際測量數據可推算（以 n ≥ 100 的點為例）：
- n = 1000：T(n) / n² ≈ 1522 μs / 1,000,000 ≈ 0.001522 μs
- n = 2000：T(n) / n² ≈ 3992.8 μs / 4,000,000 ≈ 0.000998 μs
- n = 3000：T(n) / n² ≈ 8340.8 μs / 9,000,000 ≈ 0.000927 μs

**進一步驗證 O(n²) 成長**：
- n 從 1000 → 2000（2倍）：時間從 1522 → 3992.8 μs（**2.62倍** ≈ 2²）
- n 從 1000 → 3000（3倍）：時間從 1522 → 8340.8 μs（**5.48倍** ≈ 3²）
- n 從 2000 → 3000（1.5倍）：時間從 3992.8 → 8340.8 μs（**2.09倍** ≈ 1.5²）

**結論**：比值趨於穩定，且時間增長與 n² 成正比，證實 **T(n) = Θ(n²)**

## 5. 延伸討論

### 5.1 為何 SelectionSort 比較次數與輸入無關？

**演算法邏輯**：
- 外層迴圈固定執行 n-1 次
- 第 i 次迭代的內層迴圈固定執行 n-i 次比較
- 總比較次數 = Σ(n-i) for i=1 to n-1 = n(n-1)/2
- **無條件跳出或提前終止機制**（與 InsertionSort 不同）

### 5.2 實測時間仍可能有變異的原因

1. **CPU 快取效應**：
   - 連續存取 vs. 跳躍存取會影響 cache hit rate
   - 遞減序列可能造成較多 cache miss

2. **分支預測**：
   - 雖然比較次數固定，但 `if (arr[j] < arr[minIndex])` 的結果會影響分支預測器
   - 遞減序列讓此條件在初期更常為真

3. **記憶體對齊與 TLB**：
   - 不同 n 值可能導致不同的記憶體對齊
   - 影響 TLB (Translation Lookaside Buffer) 效能

### 5.3 與其他 O(n²) 排序的比較

| 演算法 | 最佳情況 | 最差情況 | 穩定性 | 自適應性 |
|--------|----------|----------|--------|----------|
| **SelectionSort** | O(n²) | O(n²) | ❌ 不穩定 | ❌ 無 |
| **InsertionSort** | O(n) | O(n²) | ✅ 穩定 | ✅ 高 |
| **BubbleSort** | O(n) | O(n²) | ✅ 穩定 | ✅ 中 |

**SelectionSort 的劣勢**：
- 無法利用輸入的部分有序性
- 即使輸入已排序，仍執行完整的 n² 比較
